# RULES.MD — правила работы над проектом Game Space

## Процесс завершения задачи
1. После КАЖДОЙ решённой задачи обязательно спросить у пользователя: **сделать ли коммиты и пуш**.
   Не пушить без явного согласия пользователя.
2. Если пользователь согласен — выполнять следующий сценарий:
   - делать **отдельный коммит на каждую задачу**;
   - сообщение коммита **на английском языке** и строго в формате префикса:
     - `fix: ...` — исправление бага
     - `add: ...` — добавление функционала
     - `update: ...` — улучшение/изменение существующего
     - `remove: ...` — удаление
      - `new: ...` — новая сущность/интеграция
      - `tool: ...` — инструменты/инфраструктура
    - **ВАЖНО:** всё, что не является кодом платформы Game Space (сборка, CI/пайплайны,
      `.gitignore`, скрипты, конфиги, документация для агентов) — коммитить **только**
      с префиксом `tool:`. Префиксы `fix/add/update/remove` использовать только для
      функционала проекта, иначе инфраструктурные коммиты попадут в Changelog релизов.
    - затем **пуш только в ветку `dev`**: `git push origin dev`.

## Ветки — жёсткое правило
- **ПУШ ТОЛЬКО В `dev`.**
- **ЗАПРЕЩЕНО** делать merge ветки `main`, merge `main` → `dev`, merge `dev` → `main`,
  а также любые пуши в `main`. Ветка `main` не трогается.

## Релизы (GitHub Releases)
- Релиз создаёт workflow `.github/workflows/build.yml` автоматически по тегу `vX.Y.Z`
  (тег аннотированный: `git tag -a vX.Y.Z -m "Описание релиза"`).
- Заголовок релиза = имя тега (например, `v0.1.0`). Тело релиза начинается сразу
  с раздела `## Changelog` — аннотация тега и любой доп. текст сверху не выводятся.
- В Changelog попадают **только** типы `fix`, `update`, `add`, `remove`; префикс
  заменяется на эмодзи, хеш коммита остаётся:
  `update: new logic automaticaly fined games` → `🔄 new logic automaticaly fined games (abc1234)`.
- Эмодзи: `fix` → 🐛, `add` → ✨, `update` → 🔄, `remove` → 🗑️.
- Типы `new`, `tool` и коммиты без префикса в Changelog **не** попадают.
